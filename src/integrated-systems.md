## 2. Integrated Systems гэж юу вэ — тодотгол

- **Хуулийн этгээд**: Integrated Systems
- **Бүтээгдэхүүний брэнд**: Integrated Systems (нэг ижил нэр, холилдохгүй)
- **Ерөнхий ангиллын нэр** (брэнд БИШ): "suh" — Сууц өмчлөгчдийн Холбоо удирдлагын категори
- **Feature/edition код нэрс**: Cosmo (AI туслах), үргэлжлүүлж Nova, Aurora гэх мэт сансрын биетүүдийн цувралаас
- **Технологи**: React SPA (Vite), Tailwind CSS, Supabase backend
- **Бизнес загвар**: **SaaS** — олон СөХ (multi-tenant) нэг платформ дээр бие даан ажиллана, тус бүр өөрийн өгөгдлөө, тохиргоогоо хардаг, өөр хэний өгөгдөлд хандахгүй

## 3. Одоогийн suh-react (admin-react)-той харилцах уялдаа

**admin-react** нь **single-tenant** (ганц СөХ)-д зориулагдсан, suh.html-ийг strangler-fig аргаар орлуулж буй систем. Үүнийг **орхихгүй, үргэлжлүүлж хөгжүүлнэ** — гэхдээ хоёр төслийн уялдааг тодорхой болгоё:

| | suh-react (admin-react) | Integrated Systems (шинэ) |
|---|---|---|
| Зорилго | Ганц бодит СөХ (одоогийн харилцагч)-д зориулсан, ажиллаж байгаа систем | Олон СөХ-д зарах, өргөжүүлэх SaaS платформ |
| CSS | Custom CSS (vanilla, `App.css`) | Tailwind (эхнээсээ) |
| Өгөгдлийн загвар | Single-tenant (tenant_id байхгүй) | **Multi-tenant** (`tenant_id`/`org_id` бүх table-д) |
| Хөгжлийн үе шат | 0-4 түвшин дүүссэн, cutover хүлээж байна | Шинээр эхэлж байна (0-р түвшин: Dashboard+Residents) |
| **Стратеги** | үргэлжлүүлж бэхжүүлнэ, cutover хүртэл асаалттай үлдэнэ | Integrated Systems-ийн код/сургамжийг АШИГЛАНА, гэхдээ шинэ codebase |

**Тодорхой чиглэл**: admin-react-ийг **Integrated Systems руу шууд шилжүүлэхгүй** (2 өөр CSS архитектур, single→multi-tenant өөрчлөлт том). Харин admin-react дээр батлагдсан **бизнес логик** (calcFee, payroll, accounting-bridge зэрэг `financeEngine.js`-үүд, permission схем) нь Integrated Systems-д **дахин ашиглагдах эх сурвалж** болно — эдгээрийг shared package (`@integrated-systems/core`) болгож задлах нь урт хугацаанд үр өгөөжтэй.

## 4. Multi-tenant архитектурын төлөвлөгөө

### 4.1 Өгөгдлийн загвар (Supabase)

- Бүх гол хүснэгэлд (`residents`, `businesses`, `transactions`, `journal_entries` гэх мэт) **`tenant_id` багана заавал** нэмнэ
- RLS policy бүрт `tenant_id = (auth.jwt() ->> 'tenant_id')::uuid` нөхцөл нэмж, tenant хоорондын өгөгдлийн алдагдалгүй тусгаарлалт баталгаажуулна
- `user_profiles` хүснэгэлд `tenant_id` (эсвэл олон tenant-д харьяалагдах боломжтой бол `user_tenants` join table)

### 4.2 Auth/routing

- Subdomain эсвэл path-based tenant тодорхойлолт (`{tenant-slug}.integratedsystems.mn` эсвэл `app.integratedsystems.mn/{tenant-slug}/`)
- Нэвтрэх үед tenant context ачаалж, `AuthContext`-д tenant мэдээллийг хадгална (admin-react-ийн `AuthContext.jsx` загвараас өргүллөж болно)
- Sidebar-ийн лого хэсэг (дээд мөр=Integrated Systems брэнд, доод мөр=tenant-ийн СөХ нэр) — үүнийг **dynamic** болгоно (өнөөдрийн scaffold-д placeholder байсан)

### 4.3 Onboarding

- Шинэ СөХ бүртгүүлэх wizard (байгууллагын мэдээлэл, эхний admin хэрэглэгч үүсгэх, эхний тохиргоо)
- Төлбөрийн загвар (subscription tier) — feature flag-аар зарим модуль (жиш нь AI Cosmo) төлбөртэй tier-д л нээгдэх боломжтой

## 5. Хөгжлийн үе шат (roadmap)

⚠️ **2026-08-10 хэрэглэгчийн тодорхой заавар**: Энэ бол Multi-СӨХ SaaS төсөл — suh-react (admin-react)-ийн цэсний бүтэц нь **single-tenant, нэг тодорхой СӨХ**-д зориулагдсан загвар тул шууд хуулбарлаж, санаачлагагүйгээр олон хуудас урьдчилан бүтээхгүй. Хэрэглэгч өөрийн **бүтцийн дизайныг төлөвлөж байгаа** (аль модуль MVP-д орох, tenant-specific vs platform-wide мэдээллийн архитектур) — энэ төлөвлөгөө бэлэн болмогц л дараагийн хуудсуудыг эхлүүлнэ. admin-react-ийг **лавлагаа/дахин ашиглах эх сурвалж** гэж үзнэ (батлагдсан бизнес логик, компонент загвар), харин цэсний жагсаалтыг үүний адил хуулбарлахгүй.

Admin-react-ийн "0-4 түвшин" загварыг өргүлж (ЗӨВХӨН ерөнхий чиглэл, тодорхой хуудасны жагсаалт биш):

- **0-р түвшин** (одоо): Auth+permission суурь, Dashboard+Residents (өнөөдөр бүтээгдсэн scaffold) — **multi-tenant БУС**, single mock tenant дээр турших
- **1-р түвшин**: Multi-tenant өгөгдлийн загвар нэвтрүүлэх (tenant_id, RLS), Auth-д tenant context нэмэх
- **2-р түвшин**: Хэрэглэгчийн төлөвлөсөн бүтцийн дагуу CRUD бүртгэлүүдийг Tailwind+DataTable component-оор бүтээх — **дэмий хуулбарлахгүй**, `<DataTable>` нэг л удаа бүтээж дахин ашиглана. **Аль модуль эхэлэхийг хэрэглэгчийн төлөвлөгөөгөөр тодорхойлно, admin-react-ийн цэсээр биш**
- **3-р түвшин**: Санхүүгийн цөм (financeEngine, accounting-bridge) — admin-react-ийн батлагдсан логикийг shared package болгож дахин ашиглана (шаардлагатай бол)
- **4-р түвшин**: SaaS давхарга — onboarding wizard, subscription/billing, tenant admin panel

## 6. Ажлын урсгал (тогтмол мөрдөх дүрэм)

1. **Компонент бүрд Rule of two**: 2 дахь удаа ижил UI бүтэц гарвал component болгож задал
2. **Playwright+mock дата-аар өөрөө баталгаажуулна** — хэрэглэгчээс screenshot асуухаас өмнө
3. **Үнэлж баттай засвар бүрийн дараа шинэ src+dist** (Дүрэм 4)
4. **Кирилл/Латин үсэг холилдохоос сэргийлсэн typo-scanner** үргэлж ажиллуулна (Дүрэм 1)
5. **Fake/algorithmic placeholder дата хэзээ ч ашиглахгүй** — цэвэр, бага тооны, `TODO`-той жишээ дата л
6. **Theme tokens (өнгө, spacing, font) эхнээсээ Tailwind config-д** — дараа нь нэмэхийг бүү хүлээ
